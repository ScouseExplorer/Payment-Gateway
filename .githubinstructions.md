# Payment Gateway / Fintech Infrastructure — Project Instructions

## 1. Project Goal

We are building a serious, production-style payment infrastructure platform inspired by systems such as Stripe, Adyen, and modern fintech payment platforms.

This is NOT intended to be a simple CRUD portfolio application.

The long-term goal is to build a technically credible payment gateway / payment infrastructure MVP that could eventually be developed into a real fintech product.

The system should demonstrate strong understanding of:

* Payment processing
* Financial ledgers
* Double-entry accounting
* Distributed systems
* Event-driven architecture
* Microservices
* Security
* Idempotency
* Fraud/risk systems
* Reconciliation
* Settlement
* API design
* Observability
* Cloud infrastructure
* Containerisation
* Kubernetes
* Financial data integrity

We will build this incrementally.

DO NOT attempt to build the entire platform at once.

# 5. Payment Engine

The payment engine is the central component.

It should support a payment-intent style flow.

Example:

POST /v1/payment-intents

Request:

{
"amount": 4999,
"currency": "GBP",
"merchantId": "merchant_123",
"customerId": "customer_123"
}

The system should create a payment intent with a controlled state machine.

Example states:

CREATED
REQUIRES_PAYMENT
PROCESSING
SUCCEEDED
FAILED
CANCELLED

The state transitions must be explicitly controlled.

Do NOT allow arbitrary status updates.

Invalid state transitions must be rejected.

# 6. Idempotency

Idempotency is mandatory for payment creation and other operations where duplicate execution could cause financial loss.

Support:

Idempotency-Key

Example:

Idempotency-Key: abc123

If the same request is submitted multiple times with the same idempotency key, it must not create multiple financial transactions.

The system should return the original result.

Design this carefully around:

* Database constraints
* Transaction boundaries
* Concurrent requests
* Race conditions
* Retry behaviour

---

# 7. Double-Entry Ledger

This is one of the most important components of the entire project.

NEVER treat a simple mutable balance field as the source of truth for financial transactions.

Use a double-entry ledger.

Every financial transaction must have balanced debit and credit entries.

Example:

Customer payment:

Debit:
Payment Clearing £100

Credit:
Merchant Balance £100

Platform fee:

Debit:
Merchant Balance £2

Credit:
Platform Revenue £2

The accounting equation must remain balanced.

Ledger entries should be immutable.

Corrections should be represented through compensating entries rather than modifying historical financial records.

The ledger should eventually support:

* Accounts
* Transactions
* Entries
* Debits
* Credits
* Currency
* Transaction references
* Metadata
* Timestamps
* Idempotency
* Audit information

The system should enforce:

Total debits == total credits

for every ledger transaction.

# 9. Refunds

Support refund workflows.

Example:

POST /v1/refunds

A refund should:

* Reference the original payment
* Validate that the payment can be refunded
* Prevent over-refunding
* Create the appropriate ledger entries
* Produce events
* Update payment/refund state
* Trigger webhooks
* Maintain an audit trail

Partial refunds should eventually be supported.

# 10. Fees

The platform should eventually support configurable fees.

Example:

Payment = £100

Fees must themselves be represented correctly in the ledger.

Do not simply subtract fees from a database balance without accounting entries.

Eventually support:

* Fixed fees
* Percentage fees
* Currency-specific fees
* Merchant-specific pricing

# 12. Fraud / Risk Engine

Create a risk module/service capable of evaluating transactions.

Initial rules can include:

* Maximum transaction amount
* Transaction velocity
* Number of transactions within a time period
* Merchant limits
* Customer limits
* Suspicious patterns
* IP/device signals where available

Potential outcomes:

APPROVE
REVIEW
DECLINE

The architecture should allow external fraud providers to be integrated later.

Potential future provider:

* Chainalysis for blockchain-related risk/compliance
* Other fraud providers where appropriate

Do not hard-code the application to one provider.

Use an abstraction such as:

RiskProvider

so providers can be swapped.

# 21. Concurrency

Assume multiple requests can happen simultaneously.

Think about:

* Duplicate payments
* Concurrent refunds
* Simultaneous balance updates
* Race conditions
* Duplicate Kafka messages
* Database deadlocks
* Retry behaviour

Do not assume requests happen sequentially.

Where money is involved, explicitly reason about concurrency.

# 30. Very Important Instruction for Copilot

DO NOT simply generate code whenever I ask a question.

Before making significant architectural changes:

1. Understand the existing codebase.
2. Identify the relevant module/service.
3. Explain the proposed change briefly.
4. Identify affected components.
5. Consider database and transaction implications.
6. Consider security implications.
7. Consider concurrency/idempotency implications.
8. Consider whether the change belongs in the current modular architecture or should eventually become a service.
9. Then implement the smallest correct change.

When I ask for code, prefer production-quality implementation over the shortest implementation.

If an implementation would create a serious financial-integrity problem, explicitly flag it.

If my proposed approach is technically unsafe for payment infrastructure, tell me why and suggest a safer architecture.

Do not hide complexity merely to make the code look simpler.
